# 일지의 형식

- 파일: `docs/journal/YYYY-MM-DD.md`. 날짜마다 하나다.
- 머리: `# 작업 일지 — YYYY-MM-DD`, 지금의 단계 (`단계: **구현** (plan 01)`), 앞의 일지의 링크.
- 스텝의 번호는 날짜를 넘어서 이어진다. 단계가 바뀌면 `---`와 새 단계의 줄을 넣는다.
- 스텝 하나가 요청 하나다. 커밋과 push만 한 스텝도 쓴다.
- 일지는 커밋의 전에 쓴다. 그래서 그 커밋의 해시는 적지 않는다. `git log`에서 본다.
- 지난 스텝은 고치지 않는다. 틀린 것은 새 스텝에 적는다.

## 스텝의 항목

해당이 없는 항목은 뺀다. 순서는 아래와 같다.

| 항목 | 내용 |
|---|---|
| **요청** 이나 **질문 (AI)** | 사용자의 말을 짧게 적는다. AI가 물었으면 선택지와 권장을 적는다. |
| **답 (사용자)** | 사용자가 고른 것. 권장과 다르면 그것도 적는다. |
| **한 일 (순서대로)** | 번호를 붙인다. 테스트의 수는 전 → 후로 적는다. |
| **검증** | 표: 검증할 내용, 결과. 실험의 표: 넣은 것, 결과. 실제의 응답의 표. |
| **결정** 이나 **결정 (AI)** | 누가 정했는지 구분한다. 문서가 정하지 않아서 AI가 정한 것은 모두 적는다. |
| **버린 대안** | 대안과 버린 이유. 대안의 좋은 점도 한 문장으로 적는다. |
| **문서** | 고친 문서와 더한 것. 승인된 문서면 "확인이 필요하다". |
| **지키지 못한 것** | 어긴 규칙과 이유. |
| **리뷰 메모** | 표: 번호, 내용, 종류 (확인, 읽음, 추정, 질문). |
| **남은 일** | 다음 작업이 해야 하는 것. plan에 넣을지 제안한다. |
| **관찰** | process에 대한 관찰. 이 스텝에서 배운 것, AI의 실수, 사용자의 교정. |

## 문장

- 짧은 평서문으로 쓴다. 한 문장에 한 가지를 쓴다.
- 숫자를 쓴다 ("테스트 30개 중 23개가 실패했다").
- AI의 실수는 "AI의 실수"로 적는다. 어떻게 알았는지와 무엇이 막았을지를 적는다.
