# ADR-0004. 검증의 방법

- 상태: 승인 (사용자가 결정, 2026-11-20). AI가 제안했다. 사용자가 묶어서 승인했다. 하나씩 보지는 않았다. 규칙마다 "출처"의 열은 제안한 쪽을 그대로 남긴다.
  - 수정 (2026-11-20): "결과"에 Python 3.9의 runner의 조건을 더했다. CI의 첫 실행이 찾았다 (일지의 스텝 25). AI가 고쳤다. 확인이 필요하다.
  - 수정 (2026-11-20): 사용자가 질문 11개에 하나씩 답했다 (일지의 스텝 8). 그 답을 반영했다. 문장은 AI가 썼다. 확인이 필요하다. 규칙 9에 `--tests tests`를 더했다. 규칙 13 ~ 15를 끝에 더했다.
  - 수정 (2026-11-21): "금지의 요구를 확인하는 방법"의 대상에 AC-2.16, AC-4.6, AC-6.7을 더했다 (일지 2026-11-21의 스텝 33). AI가 고쳤다. 확인이 필요하다.

## 이 문서를 읽는 법

요구의 수준의 키워드는 [Spec 01의 "이 문서를 읽는 법"](../spec/01-marketplace.md#이-문서를-읽는-법)을 따른다. 용어는 [Domain 01](../domain/01-marketplace.md)을 따른다.

## 맥락

- 이 저장소의 산출물은 Markdown, JSON, HTML의 틀 1개, Python 스크립트 1개다. 실행하는 애플리케이션이 없다. 프로젝트의 규칙은 "테스트를 먼저 쓴다"다.
- 사용자는 Python의 `unittest`와 GitHub Actions를 골랐다 (2026-11-20).
- `tstack-check.py trace`는 테스트의 이름에서 ID의 표지를 찾는다: `ac1_1_`, `r3_` (읽음: 스크립트). `.py`는 `trace`가 읽는 확장자다. `.sh`는 아니다.
- `claude plugin validate`는 로그인이 없이 돈다. `CLAUDE_CONFIG_DIR`는 설치를 격리한다 (확인: Spec 01의 E1, E3).
- 로컬 경로의 마켓플레이스는 플러그인을 복사하지 않는다 (확인: E4). 그래서 "설치한 사본"의 확인은 GitHub에서 설치할 때만 된다. `file://`의 URL은 쓰지 못한다 (확인: E6).
- `claude plugin eval`은 모델을 부른다. 로그인과 비용을 요구한다.
- npm의 패키지 `@anthropic-ai/claude-code`가 CLI를 설치한다 (확인: `npm view`, 2026-11-20의 버전은 `2.1.329`).

## 결정

| # | 규칙 | 출처 |
|---|---|---|
| 1 | 검사는 **반드시** Python 3의 `unittest`로 써**야 한다**. | 사용자가 결정. |
| 2 | 검사와 `scripts/`의 코드는 Python의 표준 라이브러리가 아닌 패키지를 **절대** 가져와**서는 안 된다**. | AI가 제안. `tstack-check.py`와 같은 조건이다. |
| 3 | 테스트의 함수의 이름은 **반드시** `test_<ID의 표지>_`로 시작**해야 한다**. ID의 표지는 `ac<목표>_<번호>`, `r<번호>`, `adr<ADR의 번호>_<규칙의 번호>`다. | AI가 제안. 사용자가 고른 미리보기에 이 모양이 있었다. |
| 4 | 테스트의 실패의 글은 **반드시** ID를 가져**야 한다** (예: `AC-1.3: …`). | AI가 제안. |
| 5 | `claude`를 부르는 테스트는 **반드시** 격리된 설정 폴더에서 돌**아야 한다**. | AI가 제안. |
| 6 | 검사는 사용자의 설정 폴더(`~/.claude`)를 **절대** 바꿔**서는 안 된다**. | AI가 제안. |
| 7 | `claude`가 `PATH`에 없으면, `claude`를 부르는 테스트는 건너뛴다. 환경 변수 `CI`가 `true`이면, 그 테스트는 건너뛰지 않고 **반드시** 실패**해야 한다**. | AI가 제안. |
| 8 | GitHub Actions는 push와 pull request마다 **반드시** 검사를 모두 돌**려야 한다**. CI는 git의 역사와 태그를 모두 받는다. | 사용자가 결정. 역사와 태그는 AI가 제안 (ADR-0003의 규칙 5). |
| 9 | CI는 **반드시** `tstack-check.py`의 `trace`와 `keywords`를 이 저장소의 `docs/`와 `tests/`에 돌**려야 한다**. `trace`에는 옵션 `--tests tests`를 준다. | AI가 제안. `--tests tests`는 사용자가 결정 (일지의 스텝 8의 7번). |
| 10 | GitHub에서 설치하는 테스트(AC-1.8)는 환경 변수 `TSTACK_REMOTE`가 `1`일 때만 돈다. CI는 `main`에 push한 뒤에 이 테스트를 **반드시** 돌**려야 한다**. | AI가 제안. |
| 11 | 검사는 `claude plugin eval`을 **절대** 돌려**서는 안 된다**. | AI가 제안. |
| 12 | 버전의 검사와 출처의 검사의 논리는 **반드시** `scripts/`의 함수에 있어**야 한다**. 테스트는 그 함수를 이 저장소와 임시의 git 저장소에 돌린다. | AI가 제안. |
| 13 | 검사와 `scripts/`의 코드는 Python 3.9에서 **반드시** 돌**아야 한다**. | 사용자가 결정 (스텝 8의 3번). |
| 14 | CI는 검사를 Python의 두 버전에서 **반드시** 돌**려야 한다**: 3.9와, CI가 주는 가장 높은 3.x. | 사용자가 결정 (스텝 8의 3번). |
| 15 | 검사는 ADR의 규칙마다 **반드시** 둘 중 하나를 확인**해야 한다**: 이름이 그 규칙의 ID의 표지로 시작하는 테스트가 있다, 그 규칙이 "테스트가 없는 규칙"의 표에 있다. | 사용자가 결정 (스텝 8의 4번). 문장은 AI가 썼다. |

규칙 7의 이유: 건너뛴 테스트는 통과로 보인다. CI에서 `claude`가 없으면 AC-1.4, AC-1.5, AC-1.10을 아무도 검사하지 않는다.

규칙 10의 이유: push의 전에는 GitHub에 그 커밋이 없다. push의 전에 이 테스트를 돌리면 이전의 커밋을 설치한다.

규칙 12의 이유: 버전의 검사는 "태그가 있고 파일이 바뀐 저장소"에서 실패해야 한다. 이 저장소는 그 상태가 아니다. 임시의 저장소가 그 상태를 만든다.

규칙 13과 14의 이유: Python 3.12부터 `unittest`는 테스트가 0개이면 끝의 코드 5를 낸다. 3.9는 0을 낸다 (확인: 3.9.6, 3.12, 3.13, 3.14에서 실행). 버전에 따라 결과가 다른 곳이 있다. macOS의 기본 `python3`은 3.9다.

규칙 15의 이유: `tstack-check.py trace`는 수용 기준과 domain의 규칙만 센다 (읽음: 스크립트). ADR의 규칙에 테스트가 있는지는 세지 않는다.

CI는 Claude Code의 버전을 고정하지 않는다 (AI가 제안). 사용자는 최신의 CLI로 설치한다. CI는 돌린 CLI의 버전을 출력한다.

### 금지의 요구를 확인하는 방법

"없어야 한다"의 테스트는 처음부터 통과한다. 그래서 작업자는 결함을 넣어서 실패를 본다. 대상은 테스트가 있는 `MUST NOT`의 ID다: AC-1.9, AC-2.1, AC-2.8, AC-2.10, AC-2.16, AC-4.3, AC-4.6, AC-6.7, R4, ADR-0001의 규칙 5, 그리고 이 문서의 규칙 2, 6, 11.

### 테스트가 없는 규칙

작업자의 행동을 정하는 규칙은 테스트로 확인하지 못한다. 작업자는 일지에 명령과 출력을 남겨서 확인한다.

| 규칙 | 일지에 남기는 증거 |
|---|---|
| ADR-0002의 규칙 1 (역사를 옮기지 않는다) | `git log --oneline`의 첫 커밋. |
| ADR-0002의 규칙 2 (출처 커밋에서 꺼낸다) | 꺼낸 명령과, `blob` 78개를 `git ls-tree`와 비교한 출력. |
| ADR-0003의 규칙 6 (`claude plugin tag`로 만든다) | 태그를 만든 명령과 출력. |
| ADR-0003의 규칙 7 (push한 태그를 바꾸지 않는다) | 증거가 없다. 사람의 조심이다. |

### 검사의 세 단계

| 단계 | 언제 | 무엇을 보는가 |
|---|---|---|
| 1 | 커밋의 전, CI | 파일과 매니페스트의 요구. `claude plugin validate --strict`. |
| 2 | 커밋의 전, CI | 격리된 설정 폴더에서 작업 사본의 경로를 마켓플레이스로 등록하고 설치한다 (AC-1.10). |
| 3 | push의 뒤 | 격리된 설정 폴더에서 GitHub의 마켓플레이스를 등록하고 설치한다 (AC-1.8). 설치한 사본의 파일을 본다. |

## 결과

- 좋은 점: `tstack-check.py trace`가 수용 기준과 규칙마다 테스트가 있는지 센다.
- 좋은 점: 검사가 사용자의 Claude Code의 설정을 건드리지 않는다.
- 좋은 점: 깨진 매니페스트가 `main`에 들어가면 CI가 실패한다.
- 나쁜 점: 3단계는 push의 뒤에만 된다. 결함이 공개의 뒤에 드러나는 경우가 있다.
- 나쁜 점: CI가 npm과 GitHub의 네트워크에 기댄다.
- 나쁜 점: 스킬의 글의 요구는 문장이 있는지만 본다 (Spec 01의 "받아들인 한계" 1번).
- 결정이 유효한 조건: `claude plugin validate`와 `claude plugin install`이 로그인이 없이 돈다. 이 동작이 바뀌면 규칙 5, 7, 8을 다시 본다.
- 규칙 14의 조건: GitHub의 `setup-python`이 Python 3.9를 주는 runner가 있다. 2026-11-20에는 Ubuntu 22.04와 24.04가 준다. Ubuntu 26.04(`ubuntu-latest`)는 주지 않는다 (확인: CI의 첫 실행, `actions/python-versions`의 목록). 그래서 3.9의 job은 `ubuntu-24.04`에서 돈다. 그 runner가 없어지면 규칙 13과 14를 다시 본다.

## 버린 대안

| 대안 | 좋은 점 | 버린 이유 |
|---|---|---|
| `pytest`. | 실패의 글이 읽기 쉽다. | 설치해야 하는 패키지다. 규칙 2와 맞지 않는다. |
| 셸 스크립트. | Python도 필요하지 않다. | `tstack-check.py trace`가 `.sh`를 읽지 않는다. 사용자가 이 대안을 고르지 않았다. |
| CI를 두지 않는다. | 장치가 적다. | 검사를 돌리는 것이 사람의 조심이 된다. 사용자가 이 대안을 고르지 않았다. |
| 사용자의 설정 폴더에 설치해서 확인한다. | 실제의 세션에서 스킬의 목록을 본다. | 검사가 사용자의 설정을 바꾼다. 되돌리는 일이 필요하다. |
| CI에서 `claude plugin eval`을 돌린다. | eval 사례가 깨지면 바로 안다. | 로그인의 비밀과 모델의 비용이 CI에 들어온다. |
