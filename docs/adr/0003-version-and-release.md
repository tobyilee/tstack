# ADR-0003. 버전과 릴리스

- 상태: 승인 (사용자가 결정, 2026-11-20). AI가 제안했다. 사용자가 묶어서 승인했다. 하나씩 보지는 않았다. 규칙마다 "출처"의 열은 제안한 쪽을 그대로 남긴다.
  - 수정 (2026-11-20): 사용자가 질문 11개에 하나씩 답했다 (일지의 스텝 8). 그 답을 반영했다. 문장은 AI가 썼다. 확인이 필요하다. `tstack`의 바꾼 파일의 수를 5개에서 17개로 고쳤다.

## 이 문서를 읽는 법

요구의 수준의 키워드는 [Spec 01의 "이 문서를 읽는 법"](../spec/01-marketplace.md#이-문서를-읽는-법)을 따른다. 용어는 [Domain 01](../domain/01-marketplace.md)을 따른다.

## 맥락

- 플러그인 매니페스트가 버전을 고정하면, 그 글자가 바뀔 때까지 사용자는 설치한 사본을 그대로 쓴다 (읽음 (agent): 브레인스토밍의 D4).
- 그래서 버전을 올리지 않은 push는 사용자에게 가지 않는다. 사람이 잊기 쉬운 규칙이다.
- 사용자는 "버전을 고정하고 검사가 지킨다"를 골랐다 (2026-11-20).
- `claude plugin tag`는 `<플러그인의 이름>--v<버전>`의 git 태그를 만든다. 플러그인 매니페스트와 플러그인의 항목의 버전이 같은지 검사한다 (확인: `claude plugin tag --help`).
- 출처 저장소의 `tstack`의 버전은 `0.1.0`이다. 출처의 `explain-diff`는 플러그인이 아니어서 버전이 없다.

## 결정

첫 릴리스의 버전은 `tstack` `0.2.0`, `explain-diff` `0.1.0`이다 (AI가 제안).

- `tstack`을 `0.2.0`으로 하는 이유: 이 저장소의 `tstack`은 출처의 `0.1.0`과 내용이 다르다 (바꾼 파일 17개, 새 파일 1개). 같은 숫자가 다른 내용을 가리키지 않게 한다.

| # | 규칙 | 출처 |
|---|---|---|
| 1 | 플러그인 매니페스트는 **반드시** `version`을 가져**야 한다**. | 사용자가 결정. |
| 2 | 버전의 유일한 자리는 플러그인 매니페스트다. 플러그인의 항목은 `version`을 **절대** 가져**서는 안 된다** (R4). | AI가 제안. |
| 3 | 릴리스의 태그의 이름은 **반드시** `<플러그인의 이름>--v<버전>`이어**야 한다**. | AI가 제안. `claude plugin tag`가 만드는 이름이다. |
| 4 | 버전의 검사는 플러그인마다 **반드시** 마지막 릴리스의 태그와 지금의 작업 트리를 비교**해야 한다**. 비교의 범위는 플러그인의 폴더다. | 사용자가 결정 (검사). 비교의 기준은 AI가 제안 (N5). |
| 5 | 버전의 검사는 얕은 clone에서 **반드시** 실패**해야 한다**. | AI가 제안. |
| 6 | 작업자는 릴리스의 태그를 **반드시** `claude plugin tag`로 만들어**야 한다**. | AI가 제안. |
| 7 | 작업자는 push한 릴리스의 태그를 **절대** 바꿔**서는 안 된다**. 바꾸는 일은 태그를 지우는 일과 태그를 다른 커밋으로 옮기는 일이다. | AI가 제안. |

규칙 4의 "바뀌었다"의 뜻: git이 추적하는 파일의 내용이 다르다, 파일이 더해졌다, 파일이 지워졌다. git이 추적하지 않는 파일은 세지 않는다. 그 파일은 커밋한 뒤에 센다.

규칙 5의 이유: 얕은 clone에는 태그가 없다. 검사는 "태그가 없다"(AC-5.3: 통과)와 "태그를 받지 않았다"를 구분하지 못한다. 구분하지 못하는 경우는 실패다. 그래서 CI는 전체의 역사와 태그를 받는다 (ADR-0004의 규칙 8).

### 릴리스의 순서

1. 플러그인 매니페스트의 `version`을 올린다.
2. 검사를 모두 돌린다. 검사가 통과한다.
3. 커밋한다.
4. `claude plugin tag plugins/<플러그인의 이름>`을 돌린다.
5. 커밋과 태그를 push한다. push는 사용자의 지시가 있을 때 한다.

## 결과

- 좋은 점: 사용자와 작업자가 "어느 판인가"를 숫자로 말한다.
- 좋은 점: 버전을 올리는 것을 잊으면 검사가 실패한다. 사람의 조심에 기대지 않는다.
- 나쁜 점: 플러그인의 폴더의 오타 하나를 고쳐도 버전을 올려야 한다.
- 정하지 않은 것: 버전의 세 숫자 중 어느 것을 올리는가. 버전이 마지막 릴리스보다 낮아진 경우. 이 슬라이스의 검사는 "같다"만 본다.
- 결정이 유효한 조건: Claude Code가 플러그인 매니페스트의 `version`을 설치한 사본의 판으로 쓴다. 이 동작이 바뀌면 규칙 1과 2를 다시 본다.

## 버린 대안

| 대안 | 좋은 점 | 버린 이유 |
|---|---|---|
| `version`을 뺀다. 사용자는 커밋을 따라온다. | 올리는 것을 잊는 일이 없다. | 사용자가 이 대안을 고르지 않았다. 판을 숫자로 말하지 못한다. |
| 플러그인의 항목에도 `version`을 쓴다. | 마켓플레이스 매니페스트만 읽어도 판이 보인다. | 값이 두 곳에 있다. 서로 달라진다. |
| 검사가 원격의 `main`과 비교한다. | 태그가 없어도 돈다. | 릴리스하지 않은 커밋이 `main`에 있으면 기준이 릴리스가 아니다. |
| 두 플러그인이 버전 하나를 함께 쓴다. | 숫자가 하나다. | 한 플러그인만 바뀌어도 다른 플러그인의 사용자가 업데이트를 받는다. |
| `tstack`의 첫 버전을 `0.1.0`으로 둔다. | 출처와 숫자가 이어진다. | 출처의 `0.1.0`과 내용이 다르다. |
