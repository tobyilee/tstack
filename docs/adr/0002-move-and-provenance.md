# ADR-0002. 옮기는 방법과 출처의 기록

- 상태: 승인 (사용자가 결정, 2026-11-20). AI가 제안했다. 사용자가 묶어서 승인했다. 하나씩 보지는 않았다. 규칙마다 "출처"의 열은 제안한 쪽을 그대로 남긴다.
  - 수정 (2026-11-20): 사용자가 질문 11개에 하나씩 답했다 (일지의 스텝 8). 그 답을 반영했다. 문장은 AI가 썼다. 확인이 필요하다. 바꾸는 파일의 수를 6개에서 18개로 고쳤다 (맥락, 규칙 7).
  - 수정 (2026-11-21): 규칙 7의 수를 18개에서 19개로 고쳤다. 사용자가 틀의 주석을 고치기로 정했다 (일지 2026-11-21의 스텝 33). 첫 릴리스의 뒤의 수정이다. 사용자가 규칙 5 ~ 7과 AC-3.1 ~ AC-3.4를 남기는 길(바꾼 파일의 표에 줄을 더한다)을 골랐다. 문장은 AI가 썼다. 확인이 필요하다. "맥락"의 18개는 첫 릴리스의 수다. 그대로 뒀다.

## 이 문서를 읽는 법

요구의 수준의 키워드는 [Spec 01의 "이 문서를 읽는 법"](../spec/01-marketplace.md#이-문서를-읽는-법)을 따른다. 용어는 [Domain 01](../domain/01-marketplace.md)을 따른다.

## 맥락

- 이 저장소가 플러그인의 유일한 원본이 된다 (사용자가 결정, 2026-11-20).
- 출처 저장소의 git 역사에서 `tstack/`을 바꾼 커밋은 1개다. `.claude/skills/explain-diff/`를 바꾼 커밋도 1개다 (확인: `git log -- <경로>`).
- 사용자는 옮기면서 결함 4개도 고치기로 정했다. AI의 권장은 "옮기기만 한다"였다. 그래서 옮긴 것과 고친 것이 한 슬라이스에 섞인다.
- 섞이면 "조용히 바뀐 파일"을 사람이 찾기 어렵다. 옮기는 파일은 78개이고 바꾸는 파일은 18개다.
- 출처 저장소는 공개 저장소다 (확인: `gh repo view`).

## 결정

| # | 규칙 | 출처 |
|---|---|---|
| 1 | 작업자는 출처 저장소의 git 역사를 이 저장소로 **절대** 옮겨**서는 안 된다**. | AI가 제안 (브레인스토밍의 Q12). |
| 2 | 작업자는 파일을 **반드시** 출처 커밋에서 꺼내**야 한다**. 출처 저장소의 작업 트리에서 복사하지 않는다. | AI가 제안. |
| 3 | 저장소는 뿌리의 `provenance.json`에 출처의 기록을 **반드시** 가져**야 한다**. | AI가 제안. |
| 4 | 출처의 기록의 항목은 **반드시** 네 값을 가져**야 한다**: 출처의 경로(`from`), 이 저장소의 경로(`to`), 출처 파일의 git blob 해시(`blob`), 바꾼 이유(`changed`). | AI가 제안. |
| 5 | 바꾸지 않은 파일의 `changed`는 **반드시** `null`이어**야 한다**. | AI가 제안. |
| 6 | 검사는 옮긴 파일의 git blob 해시를 **반드시** 파일의 내용에서 계산**해야 한다**. 검사는 출처 저장소를 읽지 않는다. | AI가 제안. |
| 7 | 출처의 기록의 `changed`가 `null`이 아닌 항목은 **반드시** Spec 01의 바꾼 파일의 표의 19개와 같아**야 한다**. | 사용자가 결정 (결함 4개를 고친다)에서 나온다. 표는 AI가 제안. |

규칙 2의 이유: 출처 저장소의 작업 트리에는 추적하지 않는 사본(`.agents/skills/explain-diff/`)이 있다. 그 사본은 출처 커밋의 파일과 낱말 1개가 다르다 (확인: `diff -rq`).

규칙 6의 설명: git blob 해시는 `blob <바이트의 수>\0<내용>`의 SHA-1이다. Python의 표준 라이브러리로 계산한다. 그래서 CI는 출처 저장소가 없어도 AC-3.2를 검사한다.

출처의 기록이 출처 커밋과 맞는지는 검사가 보지 않는다. plan의 작업이 한 번 대조한다: 기록의 `blob` 78개를 `git ls-tree -r 68fc5e2`의 출력과 비교하고, 비교의 출력을 일지에 남긴다.

## 결과

- 좋은 점: 옮긴 파일 하나가 조용히 바뀌면 검사가 실패한다.
- 좋은 점: 누구나 출처 커밋의 URL에서 출처 파일을 본다.
- 나쁜 점: `git blame`이 출처 저장소로 이어지지 않는다.
- 나쁜 점: 첫 릴리스의 뒤에 플러그인의 파일을 고치면, 그 파일의 항목을 `changed`로 바꿔야 한다. 고친 파일이 늘면 이 일이 부담이 된다.
- 결정이 유효한 조건: 첫 릴리스까지다. 첫 릴리스의 뒤에 플러그인의 파일을 고치는 슬라이스는 규칙 5 ~ 7과 AC-3.1 ~ AC-3.4를 남길지 먼저 정한다 (Spec 01의 "받아들인 한계" 2번).

## 버린 대안

| 대안 | 좋은 점 | 버린 이유 |
|---|---|---|
| `git filter-repo`나 `git subtree split`으로 역사를 옮긴다. | `git blame`과 `git log`가 이어진다. | 옮길 역사가 경로마다 커밋 1개다. 경로를 다시 놓는 일이 역사의 값보다 크다. |
| 출처 저장소를 git submodule로 둔다. | 복사하지 않는다. | 이 저장소가 유일한 원본이 되지 않는다. 출처 저장소의 사본은 슬라이스 2에서 지운다. |
| 출처의 기록이 없이 복사한다. | 파일 하나와 검사 하나가 줄어든다. | 옮긴 것과 고친 것이 섞였을 때 조용한 변경을 잡지 못한다. |
| 옮기기만 하고 결함은 다음 슬라이스에서 고친다. | "출처와 같다"의 검사에 예외가 2개뿐이다. | 사용자가 이 대안을 고르지 않았다. 공개하는 첫 판에 결함 3개가 남는다. |
